Claude Code 團隊還需要 code review 嗎？

长图

答

结论

需要。 核心改動由 code owner 親自審，外圍改動交給 review bot，漏掉的問題再變成測試，讓 bot 越來越準。

  1. 產品工程約 65% 的 PR 由內部版 Claude 合併，但核心程式仍有人親自看。1
  2. 人工審查是一塊一塊撤掉的，花了六個多月。1
  3. 信任來自 eval：每次事故的 PR 都加進測試集。1
  4. 給 AI 的指示變短了，少寫禁令，多給背景。1

人工審查怎麼撤掉？

  1. 全部人審

    一開始每個改動都由人審。

  2. 看 bot 抓得準不準

    按檔案範圍觀察，bot 是否抓到全部問題。

  3. 一塊一塊放手

    某塊抓到 100% 的問題，才撤掉那塊的人工。

  4. 核心永遠有人

    最關鍵的改動仍由 code owner 手動審。

照實講的地方

「抓到 100%」是 Cat Wu 說的撤人工條件，訪談沒講怎麼量。 整個過程花了六個多月，不是一次換掉。

3

漏掉的問題怎麼變成測試？

图的结构
  • 發生事故 incident
  • 找出造成的 PR find
  • 改 review bot improve
  • PR 加進 eval add
  • 跑 eval 不退步 gate
  • add → gate · 每次改動
  • find → improve · 為何沒抓到
  • improve → add
  • incident → find
  1. 找出造成的 PR ↗

    事故檢討時回頭找那個 PR，問 review 要怎麼改才抓得到。

  2. PR 加進 eval ↗

    漏掉一次，測試集就多一個案例。

  3. 跑 eval 不退步 ↗

    之後改 bot 或換新模型，都先整套跑過，跑贏才換。

使用者抱怨的行為也一樣處理：排優先序，一個一個做成行為測試。Cat Wu 也承認覆蓋還沒到 100%。1

4

給 AI 的指示怎麼寫？

面向以前現在
長度完整版更短最新模型縮短約八成
範例放很多範例拿掉範例，模型發揮更好
寫法易衝突多寫「不要做 X」多給背景
驗證規則前端改動一律驗證大幅改動介面時，才在本機跑起來看

Thariq 說，他們以前把模型限制得太多了。禁令和使用者指示衝突時，模型會搞混。1

適用範圍

這是他們對最新模型的經驗。自己的模型適不適合變短，要用自己的測試確認。
